# Tasks — server

Сервер трекера задач jedi-tasks. Собран из сервера Coin: те же слои (`endpoint/service/repository/model`),
авторизация (логин и пароль, JWT), аудит-лог и синк. Контекст предметной области — в репо `ios` (`CONTEXT.md`),
контракты — в [contracts](https://github.com/jedi-tasks/contracts).

## Состав

- `server/internal/modules/*` — модули: `auth`, `user`, `settings`, `taskList`, `listSection`, `priority`,
  `durationOption`, `task`, `tag` (вместе со связями задач и тегов), `blocker`, `auditLog`, `sync`, `transactor`.
- `server/migrations/pgsql` — миграции goose, применяются при старте.
- `server/cmd/smoke` — смоук-тест запущенного сервера.
- `server/internal/integrationTest` — интеграционные тесты сервисов на Postgres 17 в testcontainers
  (нужен Docker): `cd server && go test ./...`.
- `pkg` — сабмодуль [bonavi/pkg](https://github.com/bonavi/pkg), общая библиотека с Coin.

## Синк

- Клиент работает офлайн и отправляет мутации обычными Create/Update/Delete из своей очереди.
- `WithSyncGate`, как в Coin: мутация от устройства, которое не скачало последние изменения, отклоняется с
  `NeedToSync` — клиент делает `Sync`, `ConfirmSync` и повторяет очередь.
- Каждая мутация несёт `updatedAt` с клиента. Запись меняется, только если изменение новее сохранённого
  (побеждает последняя запись). Повторный `Create` с тем же id ничего не делает — повтор из очереди безопасен.
- Каждое применённое изменение пишется в аудит-лог; `Sync` отдаёт всё после чекпоинта устройства.
- Сервер — только центральное звено: он применяет ровно ту мутацию, что прислал клиент, и ничего не меняет
  сам. Каскадов нет: клиент сам удаляет детей до родителя, сам снимает блокеры выполненной задачи
  (`ResolveBlocker`).

## Правила целостности

Удаление мягкое (`deleted_at`). Живая строка (`deleted_at IS NULL`) не может ссылаться на удалённую; удалённая
на удалённую — может. Мутация, которая нарушила бы правило, отклоняется ошибкой `BadRequest` (категория
`Other`) с текстом для пользователя. Проверка идёт в той же транзакции, что и мутация, с блокировкой строк,
поэтому параллельные запросы правило не обойдут. Порядок удаления: связи task-tag и блокеры → задачи →
разделы → список; приоритет и тег — после задач и связей, которые на них ссылаются.

| Мутация | Отклоняется, если | Текст ошибки |
|---|---|---|
| `DeleteTaskList` | это Inbox | Inbox удалить нельзя |
| `DeleteTaskList` | в списке есть живые задачи | В списке есть задачи — сначала удалите их или перенесите в другой список |
| `DeleteTaskList` | в списке есть живые разделы | В списке есть разделы — сначала удалите их |
| `DeleteListSection` | на раздел ссылаются живые задачи | В разделе есть задачи — сначала удалите их или перенесите в другой раздел |
| `DeletePriority` | на приоритет ссылаются живые задачи | У приоритета есть задачи — сначала удалите их или смените им приоритет |
| `DeleteTag` | тег привязан к задачам живыми связями | Тег привязан к задачам — сначала отвяжите его |
| `DeleteTask` | к задаче привязаны теги | К задаче привязаны теги — сначала отвяжите их |
| `DeleteTask` | есть живой блокер, где задача заблокирована или блокирует | Задача участвует в блокерах — сначала удалите их |
| `CreateTask`, `UpdateTask`, `CreateListSection`, `UpdateListSection` | список удалён | Список удалён — выберите другой список |
| `CreateTask`, `UpdateTask` | раздел удалён | Раздел удалён — выберите другой раздел |
| `CreateTask`, `UpdateTask` | приоритет удалён | Приоритет удалён — выберите другой приоритет |
| `AddTagToTask`, `CreateBlocker` | задача удалена | Задача удалена |
| `AddTagToTask` | тег удалён | Тег удалён |

- Ссылка на чужую или несуществующую запись — `Forbidden`, как и раньше.
- Блокер выполненной задачи целостность не нарушает: сервер его не трогает, клиент снимает его сам.
- Мутация, проигравшая по времени (`updatedAt` старее сохранённого), и повторный `Create` ничего не меняют и
  не проверяются.

## Новый пользователь

Регистрация открыта только при `AUTH_SIGN_UP_ENABLED=true`. При регистрации сервер создаёт Inbox,
три приоритета «Пути джедая» и справочник длительностей — клиент получает их первым синком.

## Локальный запуск

```bash
docker compose -f localEnvironment/docker-compose.yml up -d
```

Переменные окружения — в `server/internal/config/config.go` и `pkg/database/pgsql`. Сгенерированный код
контрактов — модуль `github.com/jedi-tasks/go-server-grpc`, его публикует CI `contracts` по тегу `v*`.
